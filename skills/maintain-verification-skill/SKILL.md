# Maintain a verification skill

A feature map rots the moment the app changes. This skill is the upkeep loop for a skill generated by `/create-verification-skill` (or any project-local verification skill with a feature map). The map is lat.md/features.md: one h2 section per user-visible feature, with Sub-features, How to get to it, Driving it, Gotchas and Code under it. The unit of rigor is the feature, not every sentence: cover every feature section from source and exercise every feature live, without terminalising every bullet.

## Outcomes

Pick one, and say which:

- **clean** — every feature got source and live coverage; nothing worth changing. No diff.
- **changed** — one diff of proven doc, harness, or map corrections, left in the working tree for the owner. No commit, no branch, no PR unless the owner asked for one.
- **blocked** — coverage could not finish or a proven fix could not ship safely. Say exactly what blocked it.

## Edit scope

Only edit the verification skill's own directory (its SKILL.md and any harness scripts it owns) and the feature sections of lat.md/features.md, plus the features line of lat.md/lat.md. Leave each feature's Changes subsection and every other lat.md file alone: other steps write those. Never edit product code during a run: a behavior the map describes that the app no longer does is either doc drift (fix the map) or a product regression (report it, don't paper over it in docs).

## Pass

0. **Locate the target.** Find the verification skill to maintain: the project-local skill whose body has launch/drive sections and a feature map (usually `skills/verify-*/`). Several candidates → ask which one; none → stop and point at `/create-verification-skill` instead of inventing a target.

1. **Index hygiene.** Read lat.md/features.md and list its h2 sections. Fix missing, duplicate, or dead features, an h2 that is not a feature, a feature missing one of its five h3s, and a lat.md/lat.md without its [[features]] line. Run lat check; every section needs a leading paragraph of at most 250 characters. Re-run `etc/ice/ice-feature-facts` and compare its `triggers` and `clusters` with the map: a trigger or cluster no feature mentions is a candidate missing feature, a key or route the map lists that the facts lack is drift. Facts with `repowise`: `dead_code` suggests drift or removed features, hotspot and co-change suggest what matters and where boundaries sit, `stale: true` means re-index before trusting it, `stale: null` means unknown and is no reason to re-index; absent is fine, never install it. Otherwise lightweight; no generated inventory. lat check's "No init version recorded" warning is not a failure; never run lat init to clear it, wiring the repo is ice-wire's job. No lat.md/ or no features.md at all: stop and point at /create-verification-skill.

2. **Source wave.** One read-only subagent per feature section, launched concurrently, each handed only its own section. Each explains "how does this user-facing feature work?" from source, flags likely doc drift with citations, and returns one concise live-verification recipe. Children never drive the app and never edit files. Return shape: feature summary / source entry points / likely drift or none / one recipe.

3. **Reconcile.** Every feature section has a returned summary. Merge overlapping recipes into as few app states as practical. Spot-check cited drift; don't re-prove clean claims. Sweep recent churn for user-facing surfaces missing from the map — require a concrete source path before calling one missing.

4. **Security currency.** When the skill has a Security section: diff the manifests present against the scanners it records (a new package manager file, a new language, a new Dockerfile or *.tf) and add entries for what's missing under the same ask-before-install rule as generation; re-run each recorded tool with its version flag and report any that no longer answer, without installing a replacement. When the skill has no Security section yet, note that as drift for create-verification-skill to fill, and leave it there.

5. **Live pass.** Required even when source looks clean. The coordinator owns all driving; follow the verification skill's own launch model — one long-lived instance driven serially for servers and UIs, or a fresh isolated session per drive for short-lived CLIs (the skill's Launch section decides, not this one). Exercise every feature at least once, and hold three invariants the whole pass, whatever the failure: (1) never drive an instance you haven't health-checked since it last did something surprising — doctor before first drive, doctor on each fresh session where sessions are the unit, doctor again after any failed drive, and where doctor can't see the failure (a wedged UI state on a healthy process), reset to a known state or relaunch rather than hoping; (2) evidence captured so far survives every cleanup, checked at its named location, not assumed; (3) nothing a drive started outlives that drive's usefulness — failed-iteration residue is cleaned whether the session is stuck, exited, or shared (for a shared instance, clean the residue, not the instance). A doctor failure caused by skill drift is drift: fix it under edit scope and retry once — restart whatever the fix invalidated, nothing more — before calling the pass `blocked`. A feature that can't be reached is `verified-unreachable` only with the concrete prerequisite (auth, entitlement, OS, external state) and the route attempted; if the map omits that prerequisite, that's drift. Any harness fix from triage gets re-driven live before it lands. Final teardown happens after the last drive of the run — including those re-proofs — so nothing outlives the run (evidence stays, per the skill).

6. **Triage.** Wrong or missing user-POV description → doc drift, fix it. Working behavior the harness can't drive → harness gap, fix it; a harness fix follows the same helpers rule as generation (scripts executable, invocation documented in the skill body). App behavior that's actually broken → product gap; record it for the user, keep it out of this diff.

7. **Ship or stop.** For changed: re-read every changed file, run lat check until it passes, and leave the corrections as one uncommitted diff; report the files. For clean or blocked: no diff, report the outcome and the coverage honestly. A lat check that cannot pass is blocked, with its output.

Keep concise run notes (features covered, unreachable prerequisites, confirmed drift, outcome) in a scratch location; don't commit them.
